Formal proof of what your firmware really touches.

Ghidra lifts firmware to P-Code. ExtractIR extracts MMIO, port, MSR, protocol and BAR facts. A Lean 4 verifier checks whether every recovered access stays inside its allowed window and peripheral family. This site shows only real, trimmed reports. It does not run firmware.

Engine v3.22 · 36-target regression, 0 mismatches · Corpus: 1,695 fixed findings across 6 stacks, plus 11 P5 real targets reported separately below.

How to read a card: fixed = accesses the engine is certain about; may = accesses that are possible but not certain; verdict = the Lean checker's answer on the recovered accesses. A PASS means only that what was found stayed inside its allowed window. It is not proof the extraction is complete.

Real firmware, real violations: none so far. The P5 hunt below (11 new real targets, Oct 30, 2026) ended in an honest zero: every FAIL it met was triaged as an allowlist gap, an empty-trace coverage limit, or a deliberate probe control — not a bug.

What the engine checks (v3.22, Lean generic mode)

  • In-window addresses — every fixed access inside the architecture's MMIO window.
  • Driver confinement (bmp mode) — each driver family touches only its own peripherals.
  • Port/MSR confinement — every port/MSR entry against an architectural allowlist. v3.22 closed the CpuDxe gap with four named MSRs, each identified from Intel documentation: 0x17 IA32_PLATFORM_ID (read), 0x79 IA32_BIOS_UPDT_TRIG (microcode trigger), 0x830 IA32_X2APIC_ICR (AP bring-up), 0x982 IA32_TME_ACTIVATE (memory-encryption status). Named entries only, no blanket range; the allowlist stays index-granular, not direction-granular.
  • Clock-enable-before-use — every used STM32 peripheral's gate register touched.
  • Bounds — no computed-pointer copy/transfer with an unsound-only guard. Synthetic precision TP=17, FP=0, FN=0, TN=16 (33 cases).
  • Boundary — no must-proven access crossing a configured security boundary (violation, unknown-agent and unknown-region counts reported, never silent). Synthetic contract 16/16; Zephyr MPU trophy exactly 1 violation; SAU NS 5 / SEC 1.

Reproduce a known CVE

CVE-2026-11743 (Zephyr SF32LB QSPI, CWE-125) — a clean, copy-paste reproduce guide: pre-fix firmware FAILs naming both the read and write sites, fixed firmware PASSes. Reproducing a known bug is detection, not discovery of a new vulnerability.

Honest negative, stated on the same page: the engine does not flag eSPI CVE-2026-78119 (PASS/PASS — the parse path is invisible to the must lens). The guide never overclaims.

Honest limits (one line each)

  • Generic PASS means only "what was found stayed in-window" — not proof of security. Proven twice: CVE-2026-11743 (vulnerable firmware passed before the bounds property) and eSPI CVE-2026-78119 (still passes).
  • Stripped binaries: generic mode only — bmp mode passes vacuously on stripped input, never quote it.
  • Clock-enable v1: order-free, not must-precede; register granularity, not bit; no-RCC firmware vacuous PASS.
  • F4 USART2 invisible (Gap B, needs a redesign, not a patch); LPUART enable→disable→use not caught.
  • Boundary V1.5 scope: static profiles + learned tables + thread attribution; config-write learning design-only; a boundary violation is a necessary condition for privilege escalation, NOT proof of an exploit.
  • Non-live 21 (all-slots seeding) is DELIBERATELY NOT enabled — a finding must mean "does call", not "could call"; deferred until a labelled JSON shape exists.
  • 16-bit real mode needs a raw-binary import path plus a segmented adapter; still open.
  • Real violations found in shipped firmware: 0. The FAILs that exist are synthetic demos and Sata/Virtio's genuinely-empty traces; the MPU/SAU boundary violations are on purpose-built proof targets.
